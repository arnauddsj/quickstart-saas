# Quickstart SaaS

The starter cloned for every new SaaS: magic-link auth, organizations, admin, Stripe
plans, background jobs, email, and the documentation system that keeps an AI-driven
codebase honest. **Replace this paragraph with the product statement on day one.**

Guidance for Claude Code and any other agent working in this repository. Reference
documentation lives in [`docs/`](docs/README.md) — one topic per file, indexed there.
This file carries only what you need _without_ being told to look; anything longer
belongs in a doc (see [Comments](#comments)).

## Stack

- Node 24 (`.nvmrc`), pnpm 11 workspace (`client`, `server`), TypeScript 6.0 (pinned
  below 6.1 by typescript-eslint; TypeScript 7 is a TODO item).
- Server: Fastify 5, tRPC 11, better-auth 1.7 (magic link, admin, organization), Drizzle
  0.45 on Postgres 17, pg-boss 12, pino, zod 4, Stripe SDK 22, nodemailer or Loops,
  Sentry SDK 10 reporting to self-hosted GlitchTip.
- Client: Vue 3.5, Vite 8, vue-router 5, TanStack Vue Query 5 for server state, Pinia 4
  for UI state only, Tailwind 4, shadcn-vue on reka-ui, lucide icons, vue-sonner,
  @sentry/vue.
- Quality gates: ESLint 10 flat + Prettier, vitest 5 unit specs in both packages, vitest
  integration specs on real Postgres, Playwright E2E, GitHub Actions, pre-commit via
  simple-git-hooks. What each layer proves: [`docs/testing.md`](docs/testing.md).

## Development commands

```bash
pnpm install && cp server/.env.example server/.env
docker compose up -d          # postgres + mailpit only
pnpm dev                      # server :3000, client :5173, mail UI :8025
pnpm typecheck                # tsc -b (server) then vue-tsc -b (client)
pnpm lint && pnpm format:check
pnpm test                     # vitest, both packages, no database needed
pnpm test:integration         # server specs on a throwaway Postgres database; needs compose up
pnpm test:e2e                 # playwright; needs the compose services
pnpm db:generate              # after editing server/src/db/schema/app.ts
pnpm db:migrate               # same code that runs at boot
pnpm auth:schema              # regenerate server/src/db/schema/auth.ts
pnpm make-admin you@example.com   # fallback only: the first sign-up is the admin
```

## Architecture

The map is in [`docs/README.md`](docs/README.md). The shape:

| Server (`server/src/`)                                                | Client (`client/src/`)                                     |
| --------------------------------------------------------------------- | ---------------------------------------------------------- |
| `index.ts` boots: migrate → pg-boss → listen; `app.ts` builds Fastify | `router/` with the auth guard; `layouts/` Auth and Default |
| `config/env.ts` (zod, import-time), `config/plans.ts`                 | `services/server.ts`: tRPC client + Query helpers          |
| `auth/` better-auth + Fastify bridge                                  | `lib/auth.ts`: better-auth Vue client                      |
| `trpc/index.ts` procedure tiers; `trpc/router/*`                      | `pages/` by route; `components/ui/` shadcn (generated)     |
| `db/schema/auth.ts` generated, `db/schema/app.ts` yours               | `types/api.ts` derived from `AppRouter`                    |
| `jobs/`, `email/`, `services/`, `routes/`                             | `stores/` Pinia for UI state only                          |

Procedure tiers: `publicProcedure` → `protectedProcedure` → `adminProcedure` (app admin)
and `orgProcedure` → `orgAdminProcedure` (organization role). Details in
[`docs/auth.md`](docs/auth.md).

### Rules you need before touching anything

Each is a silent failure: it compiles, deploys, and breaks later.

- **`PUBLIC_URL` is the only origin browsers use.** Auth cookies are issued for it;
  proxies must keep `Host` (`changeOrigin: false`, `proxy_set_header Host $host`). Wrong
  value or rewritten host: login "works" and bounces forever →
  [`docs/auth.md`](docs/auth.md).
- **A failed session check is not "signed out".** `getSession()` returns an `error` on 429 or
  a down API; only `data: null` without an error means no session. Conflating them turns
  any server hiccup into a fake logout, and `/get-session` stays exempt from rate limits →
  [`docs/auth.md`](docs/auth.md).
- **Never edit `server/src/db/schema/auth.ts`.** It is generated by `pnpm auth:schema`;
  an edit is lost on regeneration and mismatches better-auth at runtime →
  [`docs/database-and-migrations.md`](docs/database-and-migrations.md).
- **Migrations apply at boot and drizzle-kit can emit `DROP COLUMN`.** Read the SQL
  before committing; a failing migration means the port never opens →
  [`docs/database-and-migrations.md`](docs/database-and-migrations.md).
- **Org-scoped data is read only through `orgProcedure`, filtered by
  `ctx.organizationId`.** Never accept an organization id from the client →
  [`docs/organizations.md`](docs/organizations.md).
- **`planGuard` runs on the server before premium work; limits exist only in
  `config/plans.ts`** → [`docs/billing.md`](docs/billing.md).
- **`createQueue` before `work` or `schedule`, and there is one `boss`** →
  [`docs/background-jobs.md`](docs/background-jobs.md).
- **Severity is the alert routing rule; messages carry no ids** →
  [`docs/error-reporting.md`](docs/error-reporting.md).
- **`EMAIL_PROVIDER` names the sender and there is no fallback** →
  [`docs/email.md`](docs/email.md).

## Type contract

Client types are **derived from the router, not restated**: `RouterOutputs` in
`client/src/types/api.ts` via `inferRouterOutputs<AppRouter>`. Do not hand-write a type
the server already describes. **Don't use `enum` for anything crossing the boundary**;
use an `as const` tuple and its companion type. **There is no transformer, so `Date`
arrives as `string`**; routers call `toISOString()` and inputs never use `z.date()`. A
`TS2339` on a call site after a server change is the contract working; fix the call,
never stub `AppRouter`. Details in [`docs/type-contract.md`](docs/type-contract.md).

## Comments

**Prose does not live in code.** Explanation lives in [`docs/`](docs/README.md); a file
that needs one points at it from the top, once.

**The file-header pointer.** A file whose behaviour is governed by a documented rule
carries one line at the top — and nothing else:

```ts
// docs/<name>.md
```

In a `.vue` file the pointer goes at the top of the `<script setup>` block with `//`;
templates carry no comments. One line, one file, one doc. Not per call site, not repeated
at each place the rule bites. If a reader needs the reasoning they open the doc; if they
don't, the code stays readable. Two docs may be listed if the file genuinely straddles
both, but three is a sign the file is doing too much.

**Delete.** Everything that explains rather than disambiguates:

- Restating the code below it — `// Fetch the user`, `/** Get the queue */`.
- Section banners — `// ===== HELPERS =====`, `// State` — and template layout labels,
  `<!-- Header -->`. A banner is usually a symptom of a file that wants splitting.
- **Teaching prose, however true.** This is the common failure and it looks helpful,
  which is why it survives review. The doc already says it; a second copy only drifts.

**Keep inline — only when necessary, scoped, and resolving a real ambiguity.** The test
is not "is this true or useful" but "without this line, would a competent reader misread
_this specific expression_". That is a narrow set:

- Compiler and tool directives — `@ts-expect-error`, `eslint-disable` — with their
  justification.
- `TODO`, when it names the condition that would resolve it.
- Licence headers.
- A value or expression whose meaning is genuinely unrecoverable from the code. Mark
  these `@keep:` so a cleanup sweep does not remove them:

  ```ts
  // @keep: FNV-1a, >>> 0 to keep it unsigned after the 32-bit multiply overflows.
  ```

  The reason is mandatory — `@keep:` with nothing after it is prose smuggled past the
  sweep.

If it takes more than two lines, it is an explanation, not a disambiguation: it belongs
in the doc.

**Writing the doc.** Check whether one already covers the topic and extend it rather than
adding a near-duplicate — and check it is not stale before building on it. See
[`docs/README.md` § Adding a doc](docs/README.md). If the rule is already in _this_ file,
point here (`// CLAUDE.md § <section>`) rather than restating it in `docs/`.

## Commits

Conventional Commits, imperative mood, one logical change per commit:
`feat(billing): map Stripe price ids through PLANS`. The body says why, not what. No AI
attribution lines. A sibling project's log reads `up`, `u`, `fix`; that is what this
rule prevents.

## Multi-step work

For anything beyond a small change, write `GATES.md` at the repo root first: one checkbox
per outcome, each with a runnable `CHECK:` and an `EXPECT:`, then work until every box
carries real `EVIDENCE:`. Delete the file when the work lands. A report is a set of claims
backed by that ledger, never a feeling of completion.

## Working style

**Tradeoff:** these guidelines bias toward caution over speed. For trivial tasks, use
judgment.

### 1. Think before coding

**Don't assume. Don't hide confusion. Surface tradeoffs.** State assumptions explicitly.
If multiple interpretations exist, present them rather than picking silently. If a
simpler approach exists, say so. If something is unclear, stop, name what is confusing,
and ask.

### 2. Simplicity first

**Minimum code that solves the problem. Nothing speculative.** No features beyond what
was asked, no abstractions for single-use code, no configurability nobody requested. If
you write 200 lines and it could be 50, rewrite it. Ask: would a senior engineer say this
is overcomplicated?

### 3. Surgical changes

**Touch only what you must. Clean up only your own mess.** Match existing patterns.
Remove imports, variables and functions that _your_ change made unused; do not remove
pre-existing dead code unless asked. Every changed line should trace directly to the
request.

### 4. Goal-driven execution

**Define success criteria. Loop until verified.** "Add validation" becomes "write the
spec for invalid inputs, then make it pass". "Fix the bug" becomes "write a test that
reproduces it, then make it green". Strong criteria let you loop independently; weak
ones ("make it work") need constant clarification.
